Workload Migration from me-central-1 to eu-west-1 (At RAK Bank)

▼
Problem Statement:
• Due to unforeseen fallout of geopolitical tensions, the bank needed to migrate its workloads from the me-central-1 region to the more stable eu-west-1 region.
• Two out of three availability zones in the me-central-1 region were affected, leading to service disruptions.
• The production environment was at risk of complete outage due to the loss of critical infrastructure.
The Ask:
• DevOps Team was asked to quickly migrate all workloads to the eu-west-1 region with minimal downtime and data loss. This was quite challending since the entire infra and application dependencies needed to be provisioned ground up.
Action plan and implementation:
• Provision the infra first, starting with basic AWS services like RDS, S3, S3 notification, SNS, ECR etc. Ensure the RDSsecurity group's CIDR range had correctly chosen VPC range to allow incoming connections emanating from within the VPC and also from on-prem hosted DBs.
• Once done, get the DBA team to restore data into the recently provisioned RDS instance.
• Provision the EKS, cluster-autoscaler/karpenter along with mandatory and optional addons.
• Create the istio NLB and get the certificate's CN and SAN mapped with the DNS name of NLB.
Technologies Used:
• AWS Services: RDS, S3, SNS, ECR, EKS, VPC, Security Groups
• Kubernetes: Cluster Autoscaler, Karpenter, Istio, NLB
• DevOps Tools: Terraform, GitHub Actions
Challenges faced:
• Constant follow ups from stakeholders.
• Terraform plan and apply failures when provisioning infra from scratch, due to unavailability of S3 endpoints, lack of VPC in shared-services account=> Route53=>Hosted Zones, incorrect/missing CIDR from whitelisted security groups.
• Amending the workflows to allow the CD to run from newly provisioned github cloud runners in eu-west-1 region.

Finacle Core Banking Modernization (At RAK Bank)

▼
Problem Statement:
• Development teams released software artifacts as automatically-generated archives from SVN containing heterogeneous file types (.scr, .jasper, .class, .sql, .jsp, etc.) requiring deployment across on-premises frontend, backend, and Oracle database servers.
• Deployment instructions communicated via manual release notes created risk through human error, with no standardized mapping of file types to target destinations and deployment paths.
• The entire process was time-consuming, error-prone, and lacked traceability across development, UAT, and production environments.
Design & Solutions:
• Migrated source code from SVN to GitHub and established an intelligent CI/CD pipeline capable of automatically deducing target server paths based on file type extensions.
• Engineered a comprehensive mappings.json configuration file serving as a centralized dictionary defining deployment rules for all file types, eliminating manual documentation.
• Automated the CI process to generate deployment artifacts containing only changed files' entries and corresponding source files, then published filtered packages to JFROG for downstream consumption.
• Implemented CD workflows leveraging GitHub Actions on self-hosted runners with Ansible orchestration to extract JFROG artifacts, interpret deployment mappings, and distribute files to appropriate target servers and paths with atomic guarantees.
• Provisioned on-demand restart workflows enabling automated service recovery across frontend and backend infrastructure without manual intervention.
• Established organization-wide branching strategy and governance policies enforcing methodical promotion of deployment packages from development through UAT environments to production.
Resolution & Results:
• Achieved 50% improvement in deployment quality through elimination of manual errors and enforcement of standardized deployment procedures.
• Realized 30% efficiency gain by automating deployment path deduction, artifact filtering, and service orchestration workflows.
• Established comprehensive deployment traceability and audit trail through GitHub Actions logs and Ansible execution records.
Technologies: Podman, Trivy, Crane, OCP, Ansible, JFROG, GitHub Actions, Bash scripting, JSON configuration

Utility Server Security Hardening - DoS Vulnerability Mitigation (at Avaya)

▼
Problem Statement:
• Utility Server's /PhoneBackup/ endpoint was vulnerable to Denial-of-Service (DoS) attacks via floods of PUT/GET requests, rendering the server unavailable.
• Enterprise desk IP Phones could not authenticate themselves due to no password being saved in flat files.
• Existing authentication via URL-embedded credentials was considered insecure per CEC standards.
Design & Solutions:
• Developed a multi-option patch binary with self-extracting archive supporting install, rollback, and status commands.
• Option 1: Blocking PhoneBackup feature completely - suitable for setups with only SIP phones.
• Option 2: IP/subnet whitelisting - restricts traffic from known sources, allowing genuine requests from enterprise IP ranges.
• Option 3: Rate limiting via nginx configuration - throttles incoming request pace to prevent DoS while maintaining legitimate traffic.
Resolution & Results:
• Implemented rate limiting in nginx configuration, blocking ~67% of malicious PUT requests (340 out of 1000 succeeded).
• Validated solution using Application Layer DoS attack simulator (slowhttptest) across multiple attack vectors: Slow Body, Slow Header, Slow Read, and Range tests.
• Established comprehensive acceptance criteria with test procedures for blocking, whitelisting, and rate limiting options.
• Delivered throttled traffic handling returning "503 Unavailable" for excessive requests while allowing legitimate traffic through.
• Enabled customers and Business Partners to deploy security fixes via self-contained patch binary with rollback capabilities.
Technologies: Nginx, Rate Limiting, Bash scripting, DoS Attack Simulation, VIP configuration, HTTP security headers
